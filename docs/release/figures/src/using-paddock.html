Using Paddock: five steps, today and in v1.0.0
What a site needs for each step, what exists on main today, and what the 25 November release changes.

scores, renders, reports
Today
main, 22 Oct
  • nine model environments built by hand
  • vendor code cloned and patched by hand
  • paddock setup is a stub
  • one host
  • each model in its own process, behind a local web service
  • waits for GPU memory; resumes runs
  • shared research servers
  • largest model needs 26 GB of GPU memory
  • openpilot and VisionPilot run on a CPU
  • each site keeps its own copies
  • KITScenes 4.2 TB in full; NAVSIM test set ~95 GB
  • a closed-loop sweep: tens of GB
  • a small record per run, tracked in git
  • leaderboard and a regression gate
  • renders for 5 of 9 benchmarks
v1.0.0
25 November
  • one container image per model in the trial matrix
  • paddock setup by profile, gated by doctor
  • download scripts with checksums
  • the same runner, launching containers
  • a certification run on install
  • each run records commit, image, weight and data hashes
  • reference sizes: S one 48–96 GB GPU, open loop; M 2–4 GPUs, adds NAVSIM
  • evaluation subsets with manifests
  • results written to the customer's own location
  • a presentation-grade leaderboard
  • an evidence pack
  • an onboarding guide
Later
v1.1 and after
  • images for simulators
  • an offline bundle for air-gapped sites
  • a job queue in the browser app
  • Slurm or Kubernetes
  • L: a GPU cluster for full closed-loop sweeps
  • a shared workspace: read-only data and model stores, a writable area per user
  • a browser app: runs, videos, graphs, code, reports
